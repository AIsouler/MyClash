## 1. 输出规范（`Icons/svg/`）

### 1.1 文件骨架与几何映射

```xml
<svg xmlns="http://www.w3.org/2000/svg" width="1024" height="1024" viewBox="0 0 1024 1024">
  <g transform="translate(tx ty) scale(s)">
    ...原始内容（坐标保持原样）...
  </g>
</svg>
```

- `s  = 1024 / max(bw, bh)`
- `tx = (1024 - bw*s) / 2 - bx*s`，`ty = (1024 - bh*s) / 2 - by*s`
- `(bx, by, bw, bh)` = **可见内容包围盒**（见 §1.2）。效果：内容最长边正好 1024，另一方向等比居中留白（**已确认的语义**，非 1:1 图标不要拉伸铺满）。
- 🔒 **形状缩放只走白名单（统一化标准，2026-09-28 用户定稿，勿自行扩展）**：
  1. **默认一律不动** —— 所有图标按上面两式归一化到「最长边 = 1024」即可，不做任何与形状相关的缩放；
  2. 「**方形图案**」图标可整体等比例缩小，但**只按 §5.17 的白名单执行**，且**只有用户明确点名**某个图标"按方形图案处理"时才加进白名单；**禁止用任何形状指标自动判定**；
  3. **圆形 / 近圆形一律不动**（圆形徽章、圆角徽章、环形、八边形…）。⚠️ 别用「方形度 = 短边/长边」去筛：满圆也是 **1.000**，与方形无法区分（2026-09-28 首次自动判定即因此误伤 6 个圆形徽章，被用户当场纠正）；
  4. **国旗（America / Japan / HongKong / China / Taiwan / Singapore）一律不动**；字形、宽扁、细线稿类同样不动；
  5. 缩放只改最外层 `transform`（`translate(512+k(tx−512), 512+k(ty−512)) scale(k·s)`，绕画布中心 ⇒ 居中不变），几何 / 渐变 / 结构一字不动；白名单**分两档**：**尖角方形 −10%（`k=0.90`）**、**四角弧形的方形 −5%（`k=0.95`）**，当前名单与判定依据见 §5.17。
- ⚠️ **唯一允许的「非等比」例外：`OpenAI.svg` 用 `scale(sx sy)`**（2026-09-28 用户要求"左右两边紧贴画布边缘"）：官方矢量内容盒 256.03×259.53 ⇒ 长宽比 0.9865，等比归一后左右各留 6.75px，故把 x 单独放大 **1.336%** 补满 1024×1024 —— `translate(11.0206 10.8145) scale(3.9139042 3.8623049)`。**其余 36 个图标一律等比，别把这个例外"修回"等比**（起因、取舍与验收见 §5.18）。Flutter 侧已核：`vector_graphics_compiler` 的 `_parseSvgScale` 支持 1~2 个参数。
- `transform` 只有 `tx/ty` 全为 0 且 `s == 1` 时才省略（**整份连外层 `<g>` 一起省**，直接 `<defs>` + 图形元素；当前唯一实例是 `Patreon.svg` —— 圆正好铺满画布）。⚠️ 原文举的 `EHentai` 有误：它 `scale(1.6461000)`，必须带 `<g>`。
- **除这个最外层 `<g>` 外，不要再靠 `transform` 搬图形**：要整组平移/缩放，就**直接改坐标数值**（坐标改完若内容包围盒变了，再按上面两式重算 `tx/ty/s`）。理由：内容坐标才是这套文件的"真身"，多一层 `transform` 等于同一几何存在两套坐标 —— §5 的按坐标审计、§4.2 的回归基线全部对不上，还容易被当成 §1.3 的「无操作 `transform`」顺手删掉。2026-09-26 起 `America`（§5.11）/ `Singapore`（§5.12）的内部图案位移已写回坐标。
- 文件风格：**CRLF 换行**（全仓库 38 个文件实测都是 CRLF；写入时用 `open(..., newline="")` 保留，理由见 §5.17）、**4 空格缩进**为主（`EHentai` / `HongKong` / `Japan` / `Proxy` / `RoundRobin` / `Server` / `WorldMap` 等历史文件是 2 空格或混用，别顺手重排）、一个标签一行、属性不折行；不加 `<?xml?>` 声明。⚠️ 本节原写"LF 换行、2 空格缩进"与仓库实际不符，已按实测更正（2026-10-04）。
- 渐变坐标**不用改**：`userSpaceOnUse` 的坐标随外层 `scale` 一起缩放；`objectBoundingBox` 本来就与坐标无关。
- **默认带渐变**：每条上色 `path` 的 `fill` 用 `linearGradient`（做法与验收见 §1.4），不要写成纯色。

### 1.2 内容包围盒怎么量（关键，别用 getBBox）

- **不要用 `getBBox()`**：它不含裁剪结果，也不算滤镜/阴影产出，America / Google / Netflix 这类会明显算错。
- 正确做法：把 SVG 光栅化到 ~2048px，取 **alpha 通道**的边缘：
  - 阈值 `128` → 真实边缘（用这个定包围盒）；
  - 阈值 `3` → 连"溢出/阴影"一起算，用来判断有没有超出 viewBox。
- 用浏览器测，脚本骨架：

```js
// 载入 SVG 文本 → <img> → canvas（画布尺寸 = 按比例放大到 2048）
// 注意：cc.drawImage(img, 0, 0, W, H) 一步缩放即可，
// 带源矩形(sx,sy,sw,sh)+缩放的写法会把 SVG 画错，别用。
const upp = viewBoxW / W; // 每个像素多少用户单位
// 扫描 alpha>128 的像素，得到 x0,y0,x1,y1
const box = [vbX + x0 * upp, vbY + y0 * upp, (x1 - x0 + 1) * upp, (y1 - y0 + 1) * upp];
```

- ⚠️ 若原文件内容**超出 viewBox**（原本靠 viewport 裁掉），新文件必须补一个显式 `<clipPath>`（裁到原 viewBox 映射后的矩形），否则 Flutter 侧会把本该裁掉的部分画出来。当前 `Google.svg`、`Netflix.svg` 就是这么处理的。

### 1.3 简化规则（做，但别越界）

- **坐标统一 2 位小数**（vtracer 描摹输出默认 7 位，是体积大头）。
  - ⚠️ **已确认例外**：当路径含**短段**（弦长 ≲ 5px、控制柄 ≲ 1px）时，0.01 的量化步长等价于 **1~2° 的切向误差**，会凭空造出折角 —— 这种文件用 **3 位小数**。实例与实测见 §5.14（Global 白色 path）。改精度前先问用户。
  - ⚠️ 必须按 SVG 路径 token 重新拼装：`.996` 取整后会变成 `1`，若直接接在后面的 `.38` 前会粘成 `1.38`（形状直接错）。规则：仅当上一个数字含 `.` 且下一个以 `.` 开头时才可省略分隔符，否则补空格。数值一律不写前导 0（`.94` 而不是 `0.94`）。
- 可以删：`<?xml?>` / `<style>` / `<title>` / `<desc>`、未被引用的 `id`、无操作 `transform`、等于默认值或继承值的属性（`fill-opacity="1"`、`stop-opacity="1"`、`offset="0%"`、`fill-rule="nonzero"`…）、没有 stroke 时的 `stroke-*`、空的 `<defs>`/`<g>`。
- 可以合并：多个 `<defs>` 合成一个；无属性的 `<g>` 摊平；只有一个子元素且属性可继承（fill/stroke/fill-rule…）的 `<g>` 下移给子元素；连续同色 `<rect>` 可合成一条多子路径的 `<path>`。
- **不能**做：把 `mix-blend-mode` 从 `style` 改写成普通属性（见 §2）；把 `<style>` 的 class 内联后又留着 `<style>`；为了"简化"改动路径几何/渐变端点；**在 `<path>`/图形元素上补 `transform` 来整体搬图**（应改坐标本身，见 §1.1）。
- **整组平移要把位移量取成「最近的 2 位小数」**，别先算 `translate(−5.0642)` 再逐个四舍五入。原因：坐标是 2 位小数即硬量化，量化步长 0.01 内容单位（= canvas 0.0102px），可达的最好精度就是**半个步长**。取最近的 2 位小数值（`−5.0642 → −5.06`、`10.155 → 10.16`）时，新坐标恰好还是 2 位小数 ⇒ **零舍入、零逐顶点抖动**，残余只有一个**均匀**的 ≤0.005 内容单位。两种写法产物可能逐字节相同（`−5.0642` 四舍五入后正是 `−5.06`），但先取整的做法不保证这一点。

### 1.4 渐变效果（**统一化默认必做**，与 YouTube 同款）

**这一步不是可选项**：统一化任何图标都要带上渐变（§3 流程第 4 步），只有用户明确说"不要渐变 / 保持原样"时才跳过。做法按图标分型：

| 图标类型                     | 默认做法                                                                              | 用户指定"和 YouTube 一样"时                              |
| ---------------------------- | ------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| 单色/块状（整块一个色）      | 一条整体竖直渐变：**该色原样 → 该色 × 0.88**（保色相，最稳）                          | 换成 YouTube 的调色：`#FF4040 → #C00405`（EHentai 实例） |
| **分层多色**（多层各自成块） | **保留每条 path 与各自基色**，每层各一条渐变：**顶端 = 基色原样，底端 = 基色 × 0.88** | 同理，只改 stop 颜色，几何范围不动                       |

硬规则（两类都适用）：

1. **渐变写在变换后的 `<g>` 内部**（`<defs>` 跟着进去）→ `gradientUnits="userSpaceOnUse"` 的坐标就是**内容坐标**，与外层 `scale` 无关（§1.1）；
2. 渐变范围取**内容盒的 y 起止**，不是 `0`~`1024`（EHentai `y 0~480`、Fcm `y 0~1640`、PayPal `y 3~48`）；`x1=x2=0` 即纯竖直；
3. 方向统一 **亮端在上（`offset="0"`）、暗端在下（`offset="100%"`）**，与 YouTube 同向；
4. 每条 path 都写**显式** `fill="url(#id)"`（理由见 §2.1，别靠继承）；id 用 `<图标名小写><序号>`（`fcm1` / `paypal3`）。

⚠️ **容器已经是纯黑（或已到该色亮度下限）时**：`该色 × 0.88` 是空操作，对容器写渐变等于白写 —— **这种图标按纯色交付，别自作主张把渐变挪到白色字形上**。`Patreon.svg`（纯黑圆底 + 纯白 P）就是定稿实例：2026-10-04 先做过"白字形 `#FFFFFF → #E0E0E0`"的折中版，被用户当轮否掉，最终**整份不加渐变、无 `<defs>`**（见 §4.1）。白字形在有色容器上仍按既有惯例保持纯白（Telegram / Spotify / Line / Steam / Bitcoin）。

**分层图标的关键**：所有层用**同一对 `y1/y2`**（同一个父 `<g>` 下），这样各层"变暗比例"完全一致 → 层次与配色关系照旧，只多一层上亮下暗的 shading。**绝不能**把多层合并成一条整体渐变（Fcm 第一次就是这么错的，花色层次全丢）。

```xml
<g transform="translate(tx ty) scale(s)">
    <defs>
        <linearGradient id="paypal1" gradientUnits="userSpaceOnUse" x1="0" y1="3" x2="0" y2="48">
            <stop offset="0" stop-color="#002991" />
            <stop offset="100%" stop-color="#002480" />
        </linearGradient>
        <!-- 其余层同理，仅 stop 颜色不同 -->
    </defs>
    <path fill="url(#paypal1)" d="..." />
</g>
```

- `0.88` 是默认的"底端变暗比例"：`#002991→#002480`、`#60CDFF→#54B4E0`；想更明显用 `0.80`，想更保守用 `0.95`。
- **别删"冗余" path**：分层文件里看似被遮住的 path 可能补着外轮廓的小缺口 —— Fcm 压成 1 条剪影会差 1433 像素，且会丢层次（判断标准见 §5.7）。

**验收（必做，两条都要过）**：

1. **上亮下暗**：渲染到 1024，取 `y = 100/300/500/700/900` 的逐行不透明像素均值，整体应上亮下暗（某行突然变亮通常是该行露出了另一层 → 再在同一层内上下取两个像素确认层内单调）；
2. **层次未变**：把 `fill="url(#…)"` 换成各自基色得到"同几何平色版"，两版**逐行色阶跳变数应基本一致**（几何与层次其实由路径数据保证，同一行的 ±1 只是 30 这个阈值卡在 AA 边缘上）；两版平均像素差按"底端变暗比例 × 图标颜色/面积"而定：Fcm ≈ 15、PayPal ≈ 12、**PikPak ≈ 32（白色层被压到 224 所以偏大）**、Apple ≈ 15（/1020），**10~35 都算正常**，总体均值只应下降几个百分点。

已入库的回归基线：

| 文件          | 层数 | 渐变                                                    | 内容盒 y |
| ------------- | ---- | ------------------------------------------------------- | -------- |
| `EHentai.svg` | 1    | `#FF4040 → #C00405`                                     | 0 ~ 480  |
| `Fcm.svg`     | 4    | `#FECA45→#E0B23D`、`#FEA610→#E0920E`、`#FD830E→#DF730C` | 0 ~ 1640 |
| `PayPal.svg`  | 3    | `#002991→#002480`、`#60CDFF→#54B4E0`、`#008CFF→#007BE0` | 3 ~ 48   |

（EHentai 是"用户指定 YouTube 同款调色"的例子；Fcm / PayPal 是"默认 × 0.88"的例子。）

## 2. Flutter 兼容红线（flutter_svg → vector_graphics_compiler）

**支持的元素**：`svg, g, defs, use, symbol, mask, pattern, clipPath, linearGradient, radialGradient, stop, image, text, tspan, circle, path, rect, polygon, polyline, ellipse, line`

**会被忽略 / 语义不同**：

| 写法                                                                 | Flutter 行为                                                                                       |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `<style>`（CSS class）                                               | 打印 `unhandled element <style/>` 并忽略 → 相关元素失去样式                                        |
| `filter` + `fe*`                                                     | 忽略 → 阴影会变成**实心色块**                                                                      |
| `<mask>`                                                             | 当作 symbol（按形状裁剪），**没有亮度蒙版语义**                                                    |
| `<title>` / `<desc>`                                                 | 静默忽略（无害）                                                                                   |
| `preserveAspectRatio` / `overflow` / `version` / `class` / `p-id` 等 | 无效，可删                                                                                         |
| `mix-blend-mode` 写成**普通属性**                                    | 浏览器忽略（Flutter 认）→ 必须写在 `style="mix-blend-mode:..."`                                    |
| `xlink:href`                                                         | 统一改写成 `href`（两边都认）                                                                      |
| 根 `viewBox` 之外的溢出                                              | 两边都会裁（`flutter_svg` 的 `clipViewbox` 默认 `true`），但重要内容别依赖它，显式 `clipPath` 更稳 |

**提交前检查清单**（写个脚本跑一遍）：

1. 根节点必须是 `width="1024" height="1024" viewBox="0 0 1024 1024"`；
2. 元素都在白名单内，且没有 `<style>` / `<filter>` / `fe*` / `<mask>` / `xlink:` / `class=`；
3. 所有 `url(#id)` 与 `href="#id"` 都能解析到定义（悬空引用 = 画面直接缺块）；
4. `clipPath` 的子元素只能是形状或 `use`。
5. **`transform` 只准出现在最外层那个规范化 `<g>` 上**（正则：全文 `transform="` 命中 **0 或 1** 次；命中 1 次时形状必须是 `translate(tx ty) scale(s)`；命中 0 次即 §1.1 的「`s==1` 且 `tx=ty=0`」情形，当前仅 `Patreon.svg`）。`Icons/svg/` 现有例外只有 `Google.svg`（描摹遗留的 `<g clip-path+matrix>`）和 `HongKong.svg`（15 个 `<use rotate>`，§5.5 的 5 重对称复用）—— 新文件一律不要走这条路（§1.1）。

### 2.1 渲染器健壮性：别依赖 `fill` 继承（真机踩坑）

有些 App 内嵌的 SVG 渲染器**没有正确实现 `<svg>`/`<g>` 上的 `fill` 继承**（把根级 `fill` 当成覆盖子元素的默认值）。实测症状与改法：

| 症状                                                  | 原因                                                 | 改法                                                                      |
| ----------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------- |
| `Line.svg` 中间白色 `LINE` 字样整块变绿（本该是白字） | 根 `<svg fill="url(#a)">`，气泡 path 自己没有 `fill` | 根上**不写** `fill`；气泡 path 补 `fill="url(#a)"`，文字 `#FFF`→`#FFFFFF` |
| `WorldMap.svg` 同类风险                               | `<g fill="url(#worldmap)">` 包住 5 条 path           | 把 `fill` 下放到每条 `path` 上                                            |
| `Steam.svg` 同类风险                                  | 根 `<svg fill="#fff">` + `<symbol>` 内 path 靠继承   | 根不写 `fill`；`<symbol>` 内无 `fill` 的 path 补 `fill="#FFFFFF"`         |

**规则：`fill` 只写在真正需要上色的元素上**（`path`/`use`/形状本身），不要放在根或 `<g>` 上。

> 已验证：把 `fill` 从根/组下移到元素本身后，浏览器渲染**逐像素零差异**（Line / Steam / WorldMap 差异像素 = 0）→ 属纯加固，不改观感。

### 2.2 描摹轮廓外溢：用 `clipPath` 兜底

同色区域是**各自独立描摹**的轮廓，彼此会有 0.5–1px 的重叠/外溢。典型症状：`Singapore.svg` 下半白色区域的**底边与左右边缘露出红线**（白块轮廓比红块略小 → 红块从边缘探头）。

- 量法：渲染到 1024，统计"应在白区内（y ≥ 白块上边缘）却仍是红色"的像素数（修复前 205，修复后 0）；
- 修法：给外溢那组元素加 `clip-path`，裁到它该在的范围：

```xml
<defs>
    <clipPath id="redTop"><rect x="0" y="0" width="1024" height="514" /></clipPath>
</defs>
<path clip-path="url(#redTop)" fill="url(#gradient_0)" d="..." />
```

**坐标空间注意**：`clipPath` 被 `<g transform>` 内的元素引用时，默认按**它自身的用户坐标系**（已缩放的内容坐标）解析；若引用方在根级则按 1024 画布坐标。取一个"两种解释都落在白块上边缘附近"的值（如 514）最稳 —— 既不留透明缝，也不露红边。

- 验收：白区内红色像素 = 0，且分界行呈 红 → 1px 混色 → 白 的过渡（不能有整列透明）。

```txt
1) 取源图（png/jpg/svg）→ Icons/png/<Name>.png（命名见 §6）
2) 若只有位图 → 用 vtracer 描摹或"剪影+渐变"降级（见 3.1 / 3.2）
3) 量可见内容盒（§1.2）→ 生成 1024 版本（§1.1）+ 简化（§1.3）
4) **加渐变效果（默认必做，不用用户提）** → 按 §1.4；分层图标有硬规则，别压成一条
5) 像素校验（§7）→ 兼容性检查（§2）
6) 同步引用：脚本/配置里的 icon 链接改成 Icons/svg/<Name>.svg（§6）
7) git add + 跑 node Test/run-tests.js（改了脚本才需要）
8) 清理所有临时文件
```

### 3.1 vtracer 描摹（位图 → 矢量）

工具不在仓库里：`%LOCALAPPDATA%\MyClash\tools\vtracer.exe`（Rust CLI，**不要**用 Python 绑定，cp314 wheel 会崩）。

```powershell
# 彩色图标（默认这套参数：色聚类 + 马赛克 + 样条 + 保留抗锯齿碎片 + 2 位小数）
vtracer.exe -i in.png -o out.svg --clustering color-cluster --hierarchical cutout `
  -m spline -f 0 -p 8 -g 2 --optimize 2 --path-precision 2
```

- `-f`（filter-speckle）：源图 ≤256px 用 `0`（保碎片、MAE 更低），更大用 `2`（否则体积暴涨）。
- 输出没有 `viewBox`，坐标在**源图像素空间**；统一化时用外层 `<g transform="scale(...)">` 映射到 1024（不要烘焙进路径）。
- CLI 输出是合法的 `<?xml version="1.0"?>`，但会带生成器注释，统一化时删掉声明与注释。
- 保真度参考：144px 源图 avg MAE(144) ≈ 6；`--upscale` 放大后再描摹**更差**，别试。

### 3.2 纯色/渐变图标：剪影 + 线性渐变（体积最小，首选）

`WorldMap.svg` 就是这么来的：

1. 用 alpha 通道做二值 mask（`alpha > 127`）→ 存成 **反相**（目标形状为黑、背景为白，因为 vtracer 黑白模式把"暗"像素当前景）；
2. `vtracer.exe -i mask.png -o bw.svg --clustering bw -m spline -f 0 --optimize 2 --path-precision 2`
   → 得到 1~5 条纯色 path（带孔洞由子路径绕向表达，别乱加 `fill-rule`）；
3. 用 PIL 对**不透明像素做逐行均值并线性拟合**，确认颜色场是（近）线性的
   （WorldMap：`rms 0.11/0.13`，几乎完美 → 两个 stop 就够）；
4. 组装：`<defs><linearGradient gradientUnits="userSpaceOnUse" .../></defs>` + `<g fill="url(#...)"` 包住 path；
5. 校验：把新 SVG 与参考 PNG 都渲染到 1024，按内容盒**逐行取不透明像素均值**比色（WorldMap 每行 Δ ≤ 1/255）。

## 5. 共性瑕疵的审查与规整方法（全量回归用）

vtracer 描摹出来的图标会有几类**不放大看不出来**的边缘问题：§5.1/§5.2 是两个全量扫描器（先量化再动手），§5.3~§5.6、§5.8~§5.12 是各类瑕疵的规整手法，§5.7 是通用踩坑速查。

### 5.1 扫描器 ①：路径几何抖动（覆盖外轮廓 + 内部图案）

把每条（子）路径展平到 1024 画布坐标 → 按弧长重采样 → 与「滑动平均后的平滑版」做残差。
**只在局部曲率半径大（本应是直线/大弧）的地方统计残差**，真实尖角与小圆角会被自动排除；
再用多个窗口 W 区分毛刺发生的尺度（W8/W16 约等于 4~8px，W32/W64 是更大尺度）。

- 实测结论：本仓库绝大多数路径在 W8/W16 上的 p95 残差 < 0.3px（即**没有细尺度毛刺**）；真正有量级的是**星形**和少数描摹出来的端头（见 §4.2）。
- 注意：W64 会把「正常形状」也判成抖动（窗口比图形特征尺寸还大），别拿 W64 排名。

### 5.2 扫描器 ②：微弱硬边 / 渐变接缝

渲染到 1024，逐行逐列求相邻像素色差，取 **3~34** 之间的"小幅突变"（真实图形边界是几百，会被排除）。
能精准抓到「渐变范围没覆盖到形状」造成的横向接缝，以及「补丁路径压在另一条路径上」造成的斜向接缝。
基线：本仓库除 §4.2 列出的那几个文件外全部为 0 像素（该基线取自扫描当时）。

### 5.3 规则几何的规整（以五角星为例）

适用：正五角星、正圆、直边等**几何规则明确**的图形。

**先判断哪种比例才对**：优先按**标准比例**核对，只有确认源图本身就是非标形状时才保留实测比例。

- 正五角星 `r/R = 1/φ² = 0.381966`（{5/2} 星形多边形）；本仓库 `Singapore`/`America` 描摹结果是 0.409/0.420（接近标准，OK），`China` 已按标准比例重建。
- ⚠️ **反例（HongKong）**：当初按"保留实测比例"把 5 枚星统一到 `r/R = 0.635`，但**香港区旗的标准星是 `r/R = 0.382`**（参考图实测 0.387）→ 0.635 是描摹出来的"胖星"伪影，不是设计。要改需用户拍板。

**做法**（必须在**路径自身坐标系**里做 —— 先别套外层 `<g transform>`，这样生成的新 `d` 才与原文件坐标一致）：

1. 取顶点：解析 `M/L/C` 的**端点**（控制点不是顶点）→ 以**面积重心**为极心 → 顶点按角度聚类（tol 12°）。
   - ⚠️ 描摹路径常多出 1~2 个"边中"顶点（China 的大星就有一个 r=12.44 的伪顶点）→ 用"取半径最大的 5 簇为外顶点、最小的 5 簇为内顶点"，别用"按中位数一分为二"。
   - ⚠️ **星心/内外半径要用「星轮廓的顶点」算，不能用星形区域的像素**：像素会把实心内部点当成内凹角，算出 `r/R=0.06` 这种荒谬值；正五角星顶点按 `M/L` 顺序**奇偶交替**（`0,2,4..` 外顶点，`1,3,5..` 内凹角），按奇偶分类最稳。
2. 朝向用「5 个星尖角度的圆均值」求，别用起始点角度。
   - ⚠️ 基准角必须用**模 72° 展开后求均值**；对 5 个 72° 等分的角直接做圆周平均是退化的（单位向量和 = 0），结果必错（曾据此得到 111.5°/214.8° 的乱值）。
3. 保留每颗星自己的**中心与外接半径**（只统一 `r/R` 比例），否则会改变各星的相对大小；输出 `M…L…Z` 直线、坐标 2 位小数。
4. China 的实例：`r/R = 1/φ²`、4 个小星 `R` 统一为均值 **7.713**、大星 **R=22.129**；结果 R 抖动 0.003~0.009、角度误差 ≤0.06°、内顶点相位 36.00°、**3157 → 2024 B（-36%）**。**未**按国旗标准把每个小星的角精确指向大星中心（实测偏 ~12°，8px 显示尺寸下不可见）。
   ⚠️ 该文件事后被用户手工格式化（**4 空格 + 属性折行**，现为 2176 B），别再按流程重跑覆盖（同 §4.1 末行）。

**与参考图核对时**：用**同名特征点**求相似变换（缩放/旋转），别用外接框对齐。实测用「5 个星心」得缩放 0.8883、旋转 0.66°，而用外接框估的是 0.911 → 差 2.5%，会带来 5px 级误差。

### 5.4 粗线圆弧带的重建（以 HongKong 叶脉为例）

适用：等宽带状的叠加线条（叶脉、跑道条之类），描摹出来必然是粗细不匀的块。

1. 把参考图里的目标线分割出来（HongKong：`红 & (15×15 窗口内白色占比 > 0.62)`）→ 干净拿到 5 条叶脉的中间段。
2. **关键发现：5 条叶脉都是圆弧** —— 参考图拟合 `R = 97.19~97.70`，误差仅 1.3px。
   ⚠️ 该提取在白/红交界处会**截断两端**，所以端点不能取它，只能用来定形状。
3. **定端点（这决定了线条对不对）**：
   - 起点 = 花瓣路径上**离花朵中心最近的点**（即"白色尖端"），实测距中心 4~20px，**必须精确落在尖端上**（偏差 0，不是"差不多"）；
   - 终点 = 沿「星心 → 某个内凹角顶点」的方向、按**到星体轮廓的最小间隙**求解位置。
4. **圆心只在两点中垂线上搜（1 个自由度）**，用参考图中心线做一维最小二乘定出圆心；
   这样圆弧**精确经过起点与终点**，形状又与参考图吻合（中位残差 0.2~0.9px）。
   比「固定半径 + 自由圆心」稳，也不会出现端点跑偏。
5. **用 SVG `A`（圆弧）命令表达**：等宽带的外/内边界正好是同心的 `R±w/2` 圆弧。一条叶脉 = 外弧 + 末端半圆头 + 内弧 + 起点半圆头，`d` 约 100 字符。
   ⚠️ **`sweep-flag`：外弧/末端头/起点头都用 `1`，只有内弧返回时用 `0`**（否则弧会鼓向另一侧）。

**「线条与星分离」的量化口径**（照参考图实测，别凭感觉）：

- 参考图里线端（**含圆头**）到**星体轮廓**的最小距离稳定在 **9.7~10.2px@1024**（5 条实测）；
- 换个等价口径：线端到星心的距离 ≈ 星外接半径 + 1.6px@1024（星半径 19 → ≈20.5）；
- 线宽取 **4.6px@1024**、两端圆头、**不收尖**。

⚠️ **归属判定别搞错**（实际踩过）：曾用「中心线两端分别到 5 个星心的距离取最小」给 5 条叶脉分配归属，
结果叶脉的**内端（靠花心那一端）离别的星更近**，5 条线被整体错配 → 圆心与末端全跑偏，线条直接穿过星体。
→ 归属要用**靠星的那一端**判定，或直接做一次二分配（保证是双射）。

### 5.5 5 重对称图形：1 个图元 + `<use>` 旋转复用

设计本身就是 N 重旋转对称时（HongKong 的花瓣/叶脉/星），把 N 份描摹结果**平均成 1 份**再用 `<use>` + `rotate` 复制 —— 一致性由构造保证。

**先量不一致**（1024 画布坐标）。花心用「花瓣并集光栅图绕该点旋转 72° 与原图比差」做 Nelder-Mead 求（最优 rms 覆盖率差 0.17）。HongKong 实测：

- 5 片花瓣**内极点半径** 4.28 / 11.01 / 20.23 / 10.89 / 14.59、周长 518~552（任一片相对"5 片平均值"的平均偏差 0.41~1.02px）；
- 叶脉**终点**很一致（r=123.7~125.4 @ −25°），**起点** r = 4.1 / 8.5 / 8.8 / 12.5 / 20.2（这就是用户看到的"起点不一致"）。

**平均形状必须用「最近点对应」，不能按索引对应**：把每片花瓣按自己的极点方向旋进同一坐标系，迭代「平均环上每点 → 分别取它到 5 片轮廓的最近点 → 求均值 → 按弧长重采样(0.5px)」，12 轮收敛（位移 <0.2px）。周长差 5% 时按弧长索引平均会沿轮廓漂移，把细节抹平/错位。

**内极点重建成楔形**（平均会把 5 根方向不同的细针抹成钝角）：在 **r=30** 处切断两条边，取两切点连线的中垂方向作针轴（−60.63°），顶点放 **r=10**。半径用「花心 r<30 内白色面积」标定：r=10 时 17.5px²，原文件 17.9px²，参考 PNG 11.2px²（参考图偏低是 144px 模糊削掉细结构所致，不能当基准）。

**组装**：`<defs>` 里放三条 `<path id="petal|vein|star">`（`fill` 直接写在各自 path 上），再各 5 次 `<use href="#petal" transform="rotate(66.330+72k 280.2056 289.7698)" />`。

- 旋转中心写**内容坐标系**的值（外层仍是 `translate(-9.1884 -9.4517) scale(1.8158926)`，花心的 content 坐标 = (280.2056, 289.7698)）。
- **绘制顺序必须是「5 花瓣 → 5 叶脉 → 5 星」**：若按「花瓣+叶脉+星」逐片画，后面那片白色花瓣会盖住先画那片花瓣的叶脉起点。
- `<use>` 在 flutter_svg 里**支持**（`parser.dart::_Elements.use` 建一个带 `precalculatedTransform` 的 group + `DeferredNode`，在 `_Resolver._drawables` 里按 `url(#id)` 解析；`defs` 的 group 不会加进渲染树，所以被引用的图形不会画两遍）。引用目标是 `<path id=...>` 也可以（`addShape` 里同样 `checkForIri`）。

**已定稿参数（勿回退）**：星统一到 中心 r=137.5 @ −17.29°、`R=18.88`、朝向 32.49°（都用 5 枚实测的圆均值；原本 spread 为 r 1.4 / R 0.93 / 朝向 2.0°），**比例 `r/R` 仍是描摹值 0.6351**（见 §5.3 的反例）；叶脉 = 过「重建后的花瓣顶点 + 终点 (112.68, −52.73)（r=124.41）」、半径取 5 条拟合半径中位数 **89.04** 的圆（圆心有 2 个候选，选更接近实测圆心那个），线宽 **4.59**、两端圆头。

**验收**（浏览器 canvas；144px 用原生分辨率对照）：规范化后 vs 参考 PNG mae **7.04**、白区 IoU **0.8719**（旧版 7.11 / 0.8715）→ 四项指标都不比旧版差（说明没偏离设计）；vs 旧版 1024px mae 0.575、24px 白区 XOR = 0。

⚠️ 那次的"旧版"是**用户未提交的工作区文件**，`git show HEAD:` 里的 9372B 是叶脉重建**之前**的版本 —— 别拿 git 历史当对比基准。

### 5.6 轮廓 → 三次贝塞尔（平滑转写）

**别用「DP 抽稀锚点 + Catmull-Rom 插值」**：插值样条会留下**周期 ≈ 锚点间距（HongKong 实测 17px）的曲率波纹**，放大后就是肉眼看到的"边缘不平滑"。度量口径：只在**低曲率区**（局部半径 >120px 且距两个极点 >60px）统计「相对 ±20px 局部二次拟合的偏差」→ 原曲线 rms **0.133** / p95 0.238 / max 0.523px（均匀 ±2px 平滑只降到 0.126，不够；±8px 才到 0.050、±12px 到 0.021，但会啃掉凹口等真实细节）。

正确做法 = **按曲率选择性预平滑 + 最小二乘 B 样条拟合**：

1. 解析轮廓并展平，按 0.4~0.5px 弧长重采样；取**两个极点**（离花心最近/最远点）作为分界点。
2. **选择性平滑**：局部半径 >150px 全量平滑、<40px 完全不动（中间 smoothstep），极点 ±25px 内不动；对 ±8px 均值滤波迭代 6 次。→ 只在平坦区抹波纹，不吃真实细节。结果：位移 mean 0.115 / max 1.26px，平坦区波纹 0.133 → 0.074。
   - 若还有**发丝级细针**（描摹在极点留的 ~2.5px 长、<0.5px 宽的折返，特征是连续 ±178° 转向），用 ±4 点（=2px）滑动平均 ×2 即可抹掉（位移 max 1.26px / mean 0.04px），真实特征保留。
3. **拟合**：以两个极点为界切成两条**开放链**，各做 **clamped 三次 B 样条最小二乘拟合**（控制点 **K=20** + 二阶差分平滑项 λ=1e-4，端点固定）；再把每段解析转成三次贝塞尔（`b0=S(u0)`、`b1=b0+S'(u0)h/3`、`b2=b3−S'(u1)h/3`，用基函数及其数值导数求 S / S'）。
   **K 就是"分辨率旋钮"**：K=14 拟合约 0.24px、K=24 约 0.15px；K 越大越会把源的波纹描回去。
4. **验收**：拟合误差（对原曲线）mean 0.165 / p95 0.307 / max 0.665px；**平坦区波纹 rms 0.0010 / max 0.0053**（比原来小 130 倍）；面积 +0.01%、内极点 9.66、外极点 234.17 均不变；花瓣路径 1693 → 1513 字符（34 段贝塞尔）；vs 参考 PNG 白区 IoU 0.8719 → **0.8725**（未退化）；新旧逐像素 1024px mae **0.053**、24px 白区 XOR = 1px → **显示效果不变，只去掉亚像素波纹**。
5. 文件最终 **4172 B**（5 份重复路径变 5 个 `<use>`，再叠加本轮轮廓平滑；原 6026 B）。

### 5.7 踩坑速查

- **路径索引别靠猜**：删过 path 之后索引会整体前移。要按 `bbox` + `fill` 核对出真实映射，别用"记忆里的编号"。
- **删 path 之前先判定它的角色**：`Taiwan.svg` 的 `path#4`、Fcm 那些"被遮住"的层都是**补外轮廓缺口**的（删了会漏白）；而 HongKong 那条 `#FDFDFD` 白色补丁本身可见、压在花瓣尖端上盖住了叶脉起点，删掉只露出旗面红底 → 必须删。判断标准：**删掉后是否产生透明缺口**。
- **别拿 git 历史 / 未提交版本当对比基准**（见 §5.5 末）。
- **Catmull-Rom 张力是 1/6 不是 1/3**：写成 `/3` 会在锚点附近产生 5~6px 的过冲小鼓包。不过该方案已整体废弃（见 §5.6）。
- **Cox-de Boor 基函数索引别写反**：标准写法是局部数组 `N[0..p]` 对应全局 `i-p+j`（i 为所在的 span）；第一版从 `N[i]` 往下播 → 半圆测试残差 43.7px 才发现。**基函数一定先拿圆/半圆自测**（正确实现残差 <0.01px）。
- **别用折线化后的轮廓估曲率**：24 段/曲线的折线（弦长 ~0.7px）会贡献 ±1~5px 的假曲率尖峰（曾因此误判"波纹很大/很小"）。要解析求值（浏览器渲染采样，或按贝塞尔解析采样）。

### 5.8 几何原语化：把描摹轮廓还原成「直线 + 圆弧」

适用：设计上本来就是**直边 + 圆角/圆帽**的图标（闪电、箭头、跑道条、胶囊）。
vtracer 会把直边描成**微弯的曲线**、把圆角描成一堆曲率不匀的碎段 —— 正常尺寸看不出来，放大后就是"线条不平整"。
（2026-09-24 用于 `Auto.svg` 闪电与 `Bypass.svg` 三条路径；与 §5.6 的"平滑转贝塞尔"是两条路线：那边保留原拓扑只去波纹，这边直接换成精确原语。）

**先度量**：按 0.25px 弧长重采样轮廓，用**解析切向**求 κ(s)（别用折线估，见 §5.7），把每个采样分类并合并成游程：

- `L`：`|κ| < 1/260px`；`C`（尖角团）：`|κ| > 1/8px`（等效半径 < 8px）；其余 `A`。
- 关键认识：**"直边"的判据是 κ 小，不是"离弦近"** —— 微弯直边的等效半径上万 px（κ 极小）却离弦 2~4px，正是要修的对象。

**重建**：

1. `L` 游程 → 两端点**直连**（弦，几何上精确的直线）；
2. `A` 游程 → 过两端点、半径取最小二乘拟合值的**精确圆弧**（圆心 = 「过两点 + 半径 r」的两个候选里离拟合圆心近的那个）；
3. `C` 游程 → 拟合半径 ≥ 6px 时同样输出圆弧（这是设计里的圆角），否则**丢弃**（当尖角处理）；
4. 单段圆弧拟合偏差 > 0.8px 时**递归二分**（在最差点切开）：混入过渡段的游程必须切开，否则会留 7~15px 偏差；
5. **边界点**：两侧切向差 < 12° 的接缝用**原轮廓点**（不动，保证不外扩）；> 12° 的尖角用两原语的**交点**，且只当交点距原接缝 < 3px 时才采用（否则保持原样，避免把圆角硬掰成尖角）。

**结果**：

- `Auto.svg` 闪电：7 条长直边的 bow（离自身弦）max **2.115 → ≈0**、rms 1.462 → 0.040（残余 0.28 是度量把直线末端与相邻圆弧算进同一游程所致，几何本身已是精确直线）；18 段贝塞尔 → 18 个原语；`d` 749 → 353 字符，文件 1559 → 1182 B；与旧渲染差 1024px **0.19%**、24px XOR = **0**；vs 参考 PNG(144) 白区 IoU **0.9312 → 0.9416**（更贴设计：旧版直边外凸）。
- `Bypass.svg` 三条路径：bow max **4.410 / 7.643 / 1.486 → 0.000**（rms 2.14/2.04/1.01 → 0）；`d` 806/475/267 → 511/285/194 字符，文件 2677 → 2144 B；与旧渲染差 1024px **1.1%**、24px XOR = 8px；vs 参考 PNG IoU 0.9610 → 0.9606（不变）。（随后两个箭头又在 §5.9 重建成等腰三角形 + 等半径圆角。）

**踩过的坑**：

- ⚠️ **圆弧不能只按 `|mid − c| = r` 去挪圆心**：这样重建出的弧**不经过端点**，SVG 渲染器会把半径**放大**到刚好连上两点，于是出现 15px 级的"尖刺/鼓包"（Bypass 箭头根部就中过招）。必须用「过两点 + 给定半径」的两个候选圆心。
- ⚠️ **> 180° 的弧不能用端点角差判方向**（会被包到 ±180 导致符号翻转）→ 用游程的**平均带符号曲率**决定 `sweep`。
- ⚠️ **针状回折**（真尖角）用「弦长/弧长 < 0.35」识别，不做圆弧、交给交点；半径 < 6px 的碎弧一律当噪声丢掉。
- 递归二分的**最小子段**取 4px：取 10px 时，若最差点落在游程端部就切不开（残差一直下不来）。
- 改的是**用户手工排版过的文件**（4 空格 + 属性折行）：只替换 `d` 属性值、其余原样保留（`Auto.svg` 的 `d` 跨两行，用正则 `d="([^"]*)"` + 空白归一化匹配，别用 ElementTree 取到的值直接 `str.replace`，XML 归一化会把换行变成空格）。

### 5.9 尖角圆角化：三角形（可调底边）+ 等半径倒角（`Bypass.svg` 右侧两个箭头）

适用：设计上是「三角/箭头尖角」，但被描摹成**一堆曲率不匀的碎弧** —— 放大后就是"三个角凸起""尖头像被切了一刀"。
与 §5.6/§5.8 不同：这里不再拟合原轮廓，而是**换成标准图元（三角形）+ 统一圆角**。
（2026-09-24 用于 `Bypass.svg` 的 path#0 / path#1 头部；轴杆、尾帽、三条路径的排版均未动。）

**做法**：

1. **定骨架**：底边取**竖直直线**（轴杆两条边端点 x 取平均：path#0 x=101.62、path#1 x=101.49）；轴线 y 取轴杆上下边中点（42.44 / 104.80）；
2. **定顶角与锚点**：`w = h·tan(α/2)`（α = 顶角）。“顶角 α / 高 h / 可见尖端位置”三个量只能定两个 —— 本图**锚定可见尖端**（让它落在参考图的 content 133.70、远离 viewBox 右边缘），再指定 **α = 66°**，`h` 随之算出（36.85）；
3. **圆角**：三个角用**同一半径 `R`** 的圆弧，切点距顶点 `t = R / tan(θ/2)`（θ 为该角的内角；等边时 1.732R）；
4. 路径顺序：底边直线 → 圆角弧 → 上边直线 → 顶角弧 → 下边直线 → 圆角弧 → 闭合。

**关键量（content 单位；canvas = content × 8.1405517 − 73.265）**：

- `R = 5.7`：三个角用**同一半径**，与轴杆肘部 5.9/9.2、尾帽 9.0 同量级 → “贴合整体风格”；
- **顶角 `α = 66°`**（参考图实测 ≈65.6° —— 设计本身就是个"胖三角"）；`R = 5.7` 时**削去量** = `R(1/sin(α/2) − 1)` = **4.77**；
- **锚定可见尖端**（content **133.70** = 参考图 133.657/133.668，canvas **1015.1**）⇒ 高 `h = 可见尖端 − 底线 x + 削去量` = **36.85 / 36.98**；底边 = `2h·tan(α/2)` = **47.86 / 48.03**（参考图 ≈48.6）；顶点 x = 138.47；两底角 = `(180−α)/2` = 57°；
- 可见上下沿 ≈ content **23.0 / 61.9**（参考图 23.0 / 61.9；旧版是 21.6 / 63.3，那才是"角凸起"）；
- 结果：canvas 可见盒 x 2..**1016**（右侧余量 **7px**，不越界）、y 99..923；vs 参考 PNG(144) 白区 IoU：等边 60°（底边 43.6）**0.9430** → **66°（底边 47.9）0.9619**（同一光栅器；跨脚本会差 ±0.3%，别混用绝对值）。

⚠️ **底边与尖端是联动的**：保持 `h`（顶点位置）不变去加宽底边 ⇒ 顶角变钝 ⇒ 削去量变小 ⇒ **可见尖端向 viewBox 右边缘移动**（`h=37.85` 时，60° 在 canvas 1015、66° 就到 1023 —— 贴着边、AA 一碰就被裁）。所以本图改成**锚定尖端**、让 `h` 跟着变（37.85 → 36.85，−2.6%，肉眼看不出来）。

**踩过的坑**：

- ⚠️ **倒角切点距离是 `R / tan(θ/2)`，不是 `R · tan(θ/2)`**（60° 时 1.732R vs 0.577R，差 3 倍）。写错时弧弦太短，SVG 渲染器会把半径**放大**到刚好连上两切点 → 圆弧**鼓到三角形外面**（可见盒被撑到 y 80..941）。
- ⚠️ **不能把"削去量"当半径**：削去量 = `R(1/sin(θ/2) − 1)`（60° 时恰好 = R）。参考 PNG 只有 144px，按弦高（sagitta）直量顶角半径得 ~3.9、按削去量反推得 ~5.5，二者不一致 → 说明设计里的"圆角"并非严格圆弧，取中间值即可（用全局拟合反推还会把顶角半径推到 8.25、底角推到 2.5，与肉眼明显不符，别信单一指标）。
- ⚠️ **拼接新头时千万別把底线交点丢掉**：新头片段通常以"底线切点"开头（如 `L101.62 29.01`），而轴杆最后一段是 `L100.86 34.22`；直接拼接会让这两点连成一条**斜线**，底线不再是竖直的（改动后肉眼看得出箭头根部微歪）。必须保留底线交点：`…L100.86 34.22 L101.62 34.32 L101.62 29.01 A…`。
- ⚠️ **别让尖端越出 viewBox**：旧版顶角弧鼓到 canvas 1030，被 `clipViewbox` 裁成平头。重建时先算 `可见尖端 = 底边 x + h − 削去量`，确保 ≤ content 134.8（canvas 1024）—— 本图尖端落在 content 134.5（canvas 1022），右侧余量仅 ~2px。
- 等边化必然压窄底边：尖端位置固定 + 60° 顶角 → 底边 43.7 而参考是 48.6；改成 `w=24` 后两者基本对齐（IoU 0.9386 → 0.9581）。注意代价是**可见尖端会随底边加宽而前移**（削去量变小）：canvas 1015.7 → 1021.8。

### 5.10 国旗统一化（长宽比 1.401066；圆角基准=未修改 HongKong：RF = 0.16375）

⚠️ **圆角基准只有一个权威值：RF=0.16375**（勿回退到 0.147419 或 0.151528）。拟合圆角必须用全弧段像素拟合并做阈值偏差校准，"纯弧点中段拟合"不可用。

- **尺寸基准**：America content 561.80×400.98（x 5.49..567.29、y 86.54..487.52）→ RATIO=W/H=1.401066。
- **做法**：各旗容器（外轮廓）解析 bbox → 保持 W 与 x 范围、H′=W/RATIO（中心不变）→ 精确圆角矩形（三次贝塞尔 K=0.5522847，同 America 遍历方向，r=RF×H′）→ transform 按 §1.1 重算（s=1024/W、tx=−x0·s、ty=(1024−H′·s)/2−y0′·s）。内部图案（星、圆、花、月）一律不动；渐变不动。
- **China 摆正**：`matrix(1 .012 -.012 1 1.682 0)` 的 d 坐标是**剪切前**的（本来就是正的）→ 直接删 5 个 `transform` 属性即可，渐变坐标同样不用动。摆正后顶边 0px 倾斜。
- **Taiwan 特殊结构**（canton 顶边/左边 = 旗面边缘，Chrome 按层合成 clip 会叠色出紫段）：红面 = 圆角矩形 **挖去**「TL 方形区 (x0n..x0n+r, y0n..y0n+r) + 顶条 (x0n..cx1, y0n..y0n+2) + 左条 (x0n..x0n+2, y0n..cy1)」（全部缺口边藏在 canton 内部下方）；canton = TL 圆角（r 同旗）矩形盖在上面。红面在 canton 右/底边保留实体 → 边缘 AA 不透明；仅 canton 左下角与右上接口处各留 ~3.6px 0.75 缝（可接受）。验证：Chrome 顶部行 maxAlpha 192→128、内部全不透明。
  ⚠️ 不能用「evenodd 挖孔 + canton 原位」：孔边与 canton 边重合处是**互补覆盖**，alpha 合成得 0.75（0.5+0.5×0.5），must 重叠不能相切。
- **Singapore 结构**：红上半（y0n→缝 511.4+2 下延压住接缝）+ 白下半（缝→y1n），删 `redTop` clip 与噪声 path；缝保持原视觉位置。
- **America 蓝区底边白垫已删**（2026-09-25 圆角统一时顺手修复）：白底 L 缺口角 314→313.4（藏进蓝区内部），`M3 313.4H300V314H3Z` 白垫整体删除——垫底+白底+蓝底三层互补叠加曾产生 alpha 219 半透明行；现在蓝底边 AA 行下是完整白底 → 全不透明。

### 5.11 内部图案在容器区块内居中（以 America 星群为例）

适用：容器里有一组**相对位置固定**的内部图案，需要整组在某个"区块"（canton / 半区 / 色块）里**光学居中**。

1. **"区块"要用渲染出来的可见范围，不要用源码里的 rect**。`America` 的蓝区 rect 是 `x=-20 w=320 y=70 h=244`，左/上都被 `flagClip` 裁掉 → 真实可见蓝区是 `x 5.49..300, y 86.54..314`（= rect ∩ clip 的 bbox）。拿 rect 的 `x=-20..300` 当中点是 **140**，而正确中点是 **152.745**，差了 12.7 内容单位、方向还是反的 —— 用户肉眼看到的问题（左边距 17.83 vs 右边距 38.14）根本修不掉。⚠️ 同理别用 `getBBox()`（不含裁剪结果，见 §1.2）。
2. **对称图形用「包围盒中心」居中，不要用面积重心**。五角星 `ymin = c_y − R`、`ymax = c_y + 0.809R`（水平方向对称），9/8 枚同形星的整体 bbox 中心才是肉眼认定的"正中心"；区块若有一角是圆角，其面积重心还会再偏 ~0.7 单位，也别用。
3. **做法：直接把这组的坐标整体加上 `(dx, dy)`**（改 `d` / `x` / `y` 数值本身，**不要**加 `transform` —— 见 §1.1），`dx = 区块中心x − 图案bbox中心x`，`dy` 同理 —— 组内相对位置严格不变。内容单位算完**不要**再乘外层 `scale`（平移和坐标同处内容坐标系）。位移量取**最近的 2 位小数**（本例名义值 `10.155` → 取 `10.16`），这样全部坐标恰好仍是 2 位小数、零舍入、零逐顶点抖动，残余只剩"半个量化步长"（见 §1.3）。
4. **验收用「光栅隔离量测」最稳**：把 SVG 文本解析成 DOM，只留目标元素（蓝区那条 / 星群那条）各自导出，`drawImage` 到 1024 canvas 后取 `alpha>128` 的包围盒，直接比较两者中心与四边余量。实测残余应 ≤0.5px（整数像素 bbox 的量化噪声；解析残差 0.01px）。
   - ⚠️ **陷阱**：隔离变体时遍历 `path,rect` 不能连 `<defs>` 里的 `clipPath` 子元素一起删 —— clipPath 空了以后引用它的整层**渲染为空白**，量测会静默返回空包围盒（全 0），看起来像"SVG 坏了"。要 `filter(e => !e.closest("defs"))`。
   - 同时跑一次**新旧逐像素比对**，确认 diff>8 的像素**全部落在「星群移动带」内**、且 alpha 通道差异为 0 → 证明旗面/蓝区/条纹逐像素未变；再在 24/64/128px 各比一次（diff 应仍全在蓝区内）。
5. **America 定稿值**：星群 bbox 中心 `(142.59, 197.40)` → 可见蓝区中心 `(152.745, 200.27)`，位移名义量 `(+10.155, +2.87)`（canvas 18.51 / 5.23px），**已写进坐标**，取 2 位小数即实际用 `+(10.16, 2.87)`。居中后蓝区内四边余量 `27.985 / 27.985`（左右）、`25.34 / 25.34`（上下）；光栅实测（整数像素 bbox，含 AA 外沿）两两相等：左右 `28.5289 / 28.5289`、上下 `25.7857 / 25.7857`，星群 bbox 与 transform 版落在**同一组像素**上（`[52,194]–[484,513]`）。**勿回退**；也**别**去改星本身的坐标（§5.3 已定稿各星中心与 R）。

### 5.12 弯月对称轴 × 内部图案：对轴与对参考图复核（以 Singapore 为例）

适用：容器里有一个**弯月形**图案，要求内部图案组与「弯月的水平分割线」对齐；或要判断内部图案组相对参考图偏大/偏小。

- **① 弯月的对称轴怎么定（三种独立口径，互验）**

弯月 = 两条圆弧围成的 lune，**对称轴就是两个圆心的连线**（不用去"看"图）：

1. **解析法（首选）**：把弯月 path 按 `M/L/C` 端点切成外弧/内弧两条子路径，各按 0.25~0.5px 弧长采样贝塞尔 → Kasa 代数初值 + Gauss-Newton 圆拟合，得 `C1/R1`、`C2/R2`；对称轴 = 过 `C1`、`C2` 的直线。
2. **尖端中点**：两弧交点即弯月两个尖端，其中点必落在轴上。
3. **光栅镜像搜索**：弯月单独渲染成 mask，搜索水平镜线 `Y` 使 `Σ|mask(x,y) − mask(x, 2Y−y−1)|` 最小（步长 0.5px；上采样 4× 可到等效 0.125px）。

Singapore 实测：`C1 (249.4028, 330.6168) R1 132.9217`（rms 0.72）、`C2 (340.9025, 330.8901) R2 142.6316`（rms 0.51）→ 轴倾角 **0.171°**、在群心 x 处 `y = 330.9212`；尖端中点 330.755；光栅镜像 330.83~330.94。三者落在 **330.8 ± 0.15**。

⚠️ **别用「弯月 bbox 的 y 中点」当轴**：尖端是细结构，144px 下 AA/阈值会把两端各削掉约 0.75px，bbox 中点会偏 0.5~0.8px。
⚠️ 轴略有倾角时要说清「在哪个 x 上取值」：**对轴 = 让图案中心点到直线的垂距为 0**。Singapore 轴倾 0.171°，在弯月自身 x 范围取值 vs 在群心 x 上取值差 0.5 单位。

- **② 「对轴」怎么改**

同 §5.11：把这组图形的坐标**整体加一个纯平移**（逐条 path 改 `d` 里的 y，**不要**加 `transform` —— 见 §1.1）。
`dy = 轴在群心 x 处的 y − 群心 y`（Singapore：`330.9212 − 335.9854 = −5.0642`，取 2 位小数 ⇒ 实际用 **−5.06**）。纯平移 ⇒ 各星 `R` / `r/R` / 臂相 / 星间距离逐位不变，只有整体位移。

- ⚠️ 用 `−5.06` 而不是 `−5.0642` 是刻意的：坐标是 2 位小数，量化步长 0.01，可达精度上限就是**半个步长**。取最近的 2 位小数值时新坐标恰好仍是 2 位小数 ⇒ **零舍入、零逐顶点抖动**，残余只是一个**均匀**的 `+0.0051` 内容单位（= 0.0052 canvas px = 144px 显示尺寸下 0.0007px）。实测 `−5.0642` 再逐个四舍五入，产物与本写法**逐字节相同**。
- ⚠️ "理想位移"本身取决于**群心的定义**：同一组 5 星，星心**圆拟合**中心给 `−5.06507`、5 星心**重心**给 `−5.09043`（差 0.025，比量化步长大 2.5 倍）。本文件统一用 ① 的**圆拟合**口径；换口径要连带更新 §4.2 的数字。

- **③ 与参考图比尺度：必须用「自归一化比值」**

144px 参考件在画布里**留有白边**（Singapore 参考图旗宽 142/144），直接比绝对像素会引入约 1.8% 假误差。要么除以同体内特征，要么用同名特征点相似变换：

- 比值口径：`星心圆半径 ÷ 旗宽`、`相邻星距均值 ÷ 旗宽`、`星心间距 ÷ 弯月高度`；
- 相似变换（§5.3 同名特征点，Umeyama）：`θ = atan2(H10−H01, H00+H11)`、`s = (cosθ·(H00+H11) + sinθ·(H10−H01)) / Σ|q|²`、`t = cp − sR·cq`，其中 `H = Σ p qᵀ`（中心化后）。**残差**同时给出"是否只是缩放+旋转"的判据（本题残差 rms 0.44px@144 ⇒ 是纯尺度差）。
  ⚠️ `s` 别用 Frobenius 形式 `√(H00²+H01²+H10²+H11²)/Σ|q|²`（会算出 0.616 这种荒谬值）；要按上式，2×2 情形等价于 `(σ1+σ2)/Σ|q|²`。

- **④ 其他踩坑**

- 光栅测量里 `ImageData` 要取 `.data` 再索引（把 `ImageData` 当数组索引会静默得到 NaN / 全 0 的空 bbox）。
- 画 SVG 到 canvas **别用「源矩形 + 缩放」形式**（`drawImage(im,sx,sy,sw,sh,dx,dy,dw,dh)`）——会把 SVG 画错（本次因此得到一个"环半径减半、比值却仍然一致"的假结果）。用 `drawImage(im,0,0,W,H)`。
- 解析校验脚本里 `path` 的**索引别按印象数**：Singapore 的 8 条 path 顺序是 `红上半 / 白下半 / 弯月 / 星A / 星B / 星C / 星D / 星E`（星从**索引 3** 起）。错 1 位会把弯月当星算，圆拟合直接跑到 1e8。
- 位移写回坐标后，校验要做三层：① 每颗星的 `ΔR / Δ(r/R) / Δ臂相 / Δ星间距离`（确认"只有整体位移"）；② **"新坐标" vs "旧坐标 + 位移量" 逐位对比**（按 `M/L` token 重解析，`Δ` 应**严格为 0**，而不是"约等于 0"）；③ 1024 / 64 / 24 三档栅格 diff（Singapore 三档均 `diffPx = 0`、`alpha diff = 0`）。

### 5.13 曲率剖面重解：修「波浪感 / 该直的没直 / 顶点错位」这类平滑缺陷

§5.1 的抖动扫描器量的是**细尺度毛刺**（W8/W16 ≈ 4~8px），抓不到「一段直 + 两处曲率跳变」这种**中尺度**缺陷（Global 左肋在 W8~W64 上 p95 全是 0.25px，扫描判它"没问题"，但放大看就是不平滑）。这类缺陷要换指标：**沿弧长看切向角 θ(s) 与曲率 κ(s)**。

判据（按可见度排序，越靠前越要命）：

| 现象                        | 指标                    | 阈值                                        |
| --------------------------- | ----------------------- | ------------------------------------------- |
| 折角                        | 接点 θ 断差             | > 0.5° 就看得出                             |
| **S 形鼓包**                | θ(s) **反向**（非单调） | 反向 > 2° 即明显                            |
| **该直的没直 / 该弯的忽直** | κ 比值跨段突跳          | > ×2 可感；「原文件就这样」不构成不修的理由 |
| 毛刺                        | §5.1 的 W8/W16 残差     | > 0.3px                                     |

**做法（Global 实例，可直接复用）**

1. **先定位"关节链"**：把有问题的连续几段（本例 `#24 tail + #25 + #26`）展平，逐段解析出 `θ(0), θ(1), κ(0), κ(1)`，找出哪些接点是"该相切却突跳"。
2. **选切点，别整段重画**：把要重建的区间从一个**内部切点**切开（de Casteljau 精确切分，切点两侧控制点都可留原值）。切点优先取 `θ = 整数角度` 的位置（本例 t=0.81399 处 θ 正好 270.000°）——接点天然 G1，且尖端等特征**原样保留**。
3. **造"目标平滑曲线"**：端点、端点切向、（可选）端点曲率是约束（本例 3 约束：终点 x、y、θ）。用**解析曲率剖面族**积分出曲线：
   `κ(s) = κ_end + (κ_0 − κ_end)·exp(−λ s^γ)`，再解 (L, κ_end, λ) 使 3 个约束精确成立（`scipy.optimize.fsolve`，残差可到 1e-11）。
   扫描 γ：γ 越小越贴原形但 s→0 处 κ 斜率越陡（γ<1 甚至发散 = 曲率拐折）；**γ≈1.2~1.6 时 max|dκ/ds| 最小**，取它。
4. **拟合成少量 G2 三次贝塞尔**：节点按弧长排布，节点处 κ 取剖面值；每段解 `c1 = P_i + a·T_i`、`c2 = P_{i+1} − b·T_{i+1}` 中的 (a,b)，使两端曲率精确等于目标：
   ```
   κ0 = (2/3)·|T0×D − b·(T0×T1)| / a²
   κ1 = (2/3)·|T1×D + a·(T0×T1)| / b²
   ```
   这样**每个内部接点都 G2**。节点分布很关键：**首段不能太短**——`κ` 骤降区若切得太碎（前几段 < 3 单位）会无正解；首段取 4 单位、后面按 ≈1.15~1.3 增长，7 段就够（本例 κ 误差 0.0006、位置偏差与 5 段版完全相同）。
   ⚠️ **验收要按"写盘后的坐标"量，不要用求解时的残差**：解出的控制点是全精度，裁剪到 2 位小数后接点 κ 会有 ≈3e-4 的相对扰动（解析端点曲率实测 Δθ ≤ 3.1e-4°、κ 相对残差 ≤ 2.8e-4）。这个量级远在视觉阈值之下，但报告里要写**实测这个数**，别写"连续到 1e-5"。
5. **验收**：① 逐接点 θ 断差 0.000°、κ 比值 ×1.000；② 重建链上 κ 单调无谷（本例 min κ = 端点值 0.00737，**没有向下的过冲**）；③ 与**原轮廓**的最近点距离（改了多少形）；④ §7 的多档栅格 diff + §2 清单。

**注意**

- 别只盯着"最小形变"：把 κ 单调化本身就会动形。本例 68 单位长的肋，形变下限约 **1.3 内容单位（2.6px@1024）**，这是"消掉 14.2° 切向反向"的必然代价——**先跟用户确认可接受的形变幅度**，或在报告里写清。
- 另一条路是「保留原来那段近直线、只把 κ 的两个突跳磨平」（曲率**带谷**的剖面族），形变能压到 0.5 单位。两条路都合法，取决于用户嫌的是"S 鼓包"还是"太直"。本例用户说的是"曲线不平滑"，按消除 S + 消直处理。
- 该区的邻居若本身也有 κ 突跳（本例 `#26/#27` ×2.5、`#27/#28` ×5.3），重建到哪一段为止要**明确划界并在回复里说明**，别静默顺手扩大范围。

### 5.14 全轮廓重拟合：把「整条路径」的折角 / κ 突跳一次性磨平

§5.13 是**局部**重建（划一段弧、解析解曲率剖面）。当缺陷**散布全轮廓**时（Global 白色 path 有 8 处折角、24 处 κ 突跳），逐段手解不现实，改用**全局最小二乘拟合**。

**方法（可直接复用）**

1. **划分跨段，绕开设计固有拐角**。先用转角扫描（窗口 4/6/9）找候选角，再**人工确认哪些是设计意图**（渲染出来看）。Global 白色 path 有 3 个必须保留的尖角：K1 `(303.37, 91.71)`（58.9°）、K2 `(347.33, 161.75)`（30.7°）、K3 `(470.23, 215.14)`（32.5°），对应 canvas `(544.1,128.4)`/`(630.4,265.9)`/`(871.6,370.6)`。以它们为端点把闭合轮廓切成 3 段，每段**两端切线方向钉死**（取原轮廓在端点处实测的进出切向）。
2. **三次 B 样条最小二乘**（clamped，`p=3`）：
   - 节点 `[0]*4 + sorted(interior) + [1]*4`，控制点数 **`NCTRL = 节点跨度数 + 3`**（写错会 `IndexError`）；
   - 端点控制点用 `P1 = A + a·TA`、`P[nctrl-2] = B − b·TB` 参数化，`a/b` 当未知量解出 ⇒ 端点切向精确成立；
   - ⚠️ **端点那两个控制点在组装正规方程时必须把常数项加上**（`const += wj*A[c]` / `wj*B[c]`）。漏掉常数项的解**完全错**（四分之一圆测试 `maxerr` 会到 35px）；补上后 `maxerr=0.005px、rms=0.003px`。调试手法：用数值雅可比逐项比对 `M` / `rhs`，能一次定位。
   - 自适应加密：先按「区间累计转角 ≤ 30°」布初始节点；再迭代把「最大误差点」处切开，直到 `maxerr ≤ tol`（tol 单位是**内容坐标**）或节点数上限。
3. **加曲率振荡惩罚（fairing）才是消 S 鼓包的关键**。只做最小二乘会**原样保留**原轮廓的 S 形鼓包。惩罚项 = 控制多边形二阶差分 `|P_{i-1} − 2P_i + P_{i+1}|²`，权重取 `lam · 样本数 / 控制点数`，直接叠加进正规方程（解仍是一次线性求解）。Global 实测：
   - `lam=0` ：S 鼓包预留 7 段（θ 反向超 2°）、`revMax 8.07°`；
   - `lam=0.002`：S 鼓包 **4 段**、`revMax 6.96°`，且**形变反而更小**（0.487→0.405px）、kink 数不变 ⇒ **甜点**；
   - `lam≥0.006`：kink 反升到 5~8 处、`dev` 涨到 0.84px ⇒ 过拟合正则，别用。
     ⚠️ 惩罚会让控制器"互相拉扯"，出现过 `lam=0.001` 时 `revMax` 暴涨到 59° 的坏解 —— **别只看单调参数，必须逐点审 kink/κ/θ**。
4. **先平滑目标点再拟合是没用的**（试过高斯 σ=1.5/3/5px 预平滑）：它只改变"短段出现在哪"，kink 数反而从 8 升到 11~19。**别走这条路**。
5. **B 样条 → 贝塞尔链**：每节点跨度出一个三次贝塞尔，`c1 = P_i + (h/3)·P'(u_i)`、`c2 = P_{i+1} − (h/3)·P'(u_{i+1})`。

**坐标精度：这里 2 位小数不够用（实测结论，例外已批准）**

量化步长 0.01 内容单位对**短段**是致命的：Global 的短段集中在高曲率处，弦长 1–4px、控制柄只有 0.35–0.85px，0.01 的舍入在这些柄上等价于 **1–2° 的切向误差** ⇒ 凭空造出折角。

- 抬高「最小段长」（`min_gap` 3/5/7/9px）**解决不了**：`min_gap=5` 只把 kink 降到 6 且 `dev` 涨到 1.02px、S 鼓包升到 5 段；`min_gap=7` 起反效果。短段在高曲率处是**结构上必需**的。

### 5.15 有官方矢量时：直接换稿，别去磨描摹稿（以 `OpenAI.svg` 为例）

用户抱怨"线条不平滑"时，**先确认仓库里这份是不是描摹稿**。像 OpenAI 这种有公开官方矢量的 logo，正确做法往往不是 §5.14 的平滑化，而是**换稿**——而且两者的**外观不一样**，必须先量化、再问用户，别自己挑。

**第 0 步：先分清"平滑度问题"还是"外观差异"。** 把两版都铺满同一画布光栅化，比**墨水占比**（alpha>128 像素数 / 画布面积）：

|          | 描摹版 `OpenAI.svg` | 官方矢量  | 结论                                                             |
| -------- | ------------------- | --------- | ---------------------------------------------------------------- |
| 墨水占比 | **48.5%**           | **38.0%** | 差 **27%** —— 描摹版辫子粗了 1/4、瓣间缝隙更浅、中心六边形孔更小 |

骨架（六瓣 logo 的拓扑与相对位置）完全一致，所以这不是"噪声"，是**比例差异**。此时给用户两个选项（换稿＝接受官方标准比例；不换＝只做 §5.14 平滑化，保留现有粗细），让用户定。OpenAI 这次用户选了换稿。

**换稿步骤**

1. **解析官方 `d`，含 `a` 弧命令**。弧转贝塞尔的公式见 §5.8；转完必须**与 resvg 对表**：把转换结果另存一份 SVG 光栅化，与原稿做 alpha 逐像素 diff（OpenAI 实测 mean 0.00006、`px>8` 0 —— 但前提是**每个子路径都重新写 `M`**，见坑 ②）。
2. **算精确内容盒**。⚠️ 别把**贝塞尔控制点**当候选极值——控制点不在曲线上，会让盒子虚假外扩（我第一版算出 `(-5.44,-3.42,266.85,263.05)`，看着像"超出 viewBox"，实际几何**恰好铺满** `0..256 × 0..259.527`）。正确做法：只对 `L` 取两端点、对 `C` 解 `d/dt = 0` 的实根再取曲线上的点。
3. **重算最外层 `transform`**（§1.1 两式）：`s = 1024 / max(bw,bh)`，`tx = (1024 - bw·s)/2 - bx·s`。OpenAI 得 `translate(6.9578 0) scale(3.9456447)`（内容 256×259.527 → 画布 1010×1024）。
4. **渐变端点按相对位置搬家**。⚠️ `OpenAI.svg` / `Bitcoin.svg` 的渐变是**用户手工调过的**（§4.1 明写"不要再按流程重跑覆盖"），不能套 §1.4 的"y 起止 / 竖直"默认值。做法：把旧端点在**旧内容盒**里的相对位置，映射到**新内容盒**（`GNEW = b_new + (GOLD - b_old)/w_old · w_new`），配色与方向一字不动。
5. **只替换 `d`**，仓库骨架（1024 画布、外层 `<g>`、4 空格缩进 + 属性折行的手写排版、渐变 id、stop 颜色）全部保留。

**注意两个反直觉的读数**

- 换稿后 **kink 数没有下降**（50 → 45）。因为官方 logo 本来就是**多边形辫子**，36 条直线段之间全是**设计尖角**（14 处 >90° 是辫子的折返尖端）。判据要看 **κ 突跳 44→0、κ 变号 44→0、Rmin 0.62→2.82px**：描摹版的"弯"是噪声（曲率沿弧长乱跳），官方版的"弯"是**真圆弧**（沿弧长恒定）。
- **p90/p99 反而上升**（p90 0.0174→0.3092）。因为官方稿有**真实的小圆角**（`a.716.716`、`a.87.87`，canvas 半径 2.86~3.5px）而描摹版把它们抹平了。**恒定的高曲率不是缺陷**，只有"沿弧长乱跳"才是。

**踩过的坑**

1. bbox 用控制点 → 假外扩（上面第 2 步）。
2. 多子路径转写时**漏写 `M`** → 8 个子路径被连成一条线，渲染成一团糊（第一次 diff 巨大，差点误判成"弧解析错了"）。
3. 审计脚本 **没按 `M` 分组** → 子路径边界被当成 `L→L 180°` 折角，凭空多出几十个 kink。要给 `parse_path` 加子路径标记，逐环审计。
4. `Rmin_canvas` 换算：κ 的单位是 **1/内容单位**，所以 `R_canvas = κ⁻¹ · SK = SK / κ`，**不是** `1/κ/SK`（后者会小 `SK²` 倍）。
5. 拿**非等比**的官方稿（256×260）直接和 1024 方形画布比像素 → 缩放不同、diff 假性 ~16。要比就先把它套上**新文件的 `transform`** 再比。

### 5.16 "只把线加粗"：用 `stroke` 做膨胀，别回头重描一遍（以 `OpenAI.svg` 为例）

用户说"改回原来的粗细 / 只改粗细度"时，**先量线宽，再动手**。

**口径 = 局部极大内切直径**：逐条水平扫描线切出每段墨迹，在段内找使"到背景的最小距离"最大的点（精确欧氏，窗口内逐点求；落在段边界被截断的点丢掉），该点直径 = 2×距离。宽度稳定的带子上这个量的**众数 = 真实带宽**；连 p10/p25/p50 一起比还能覆盖尖端、拐角这些窄处。

| `OpenAI.svg`           | 线宽 p10 / p25 / p50 / 众数 (px) | 墨水占比 |
| ---------------------- | -------------------------------- | -------- |
| 旧＝描摹稿（**目标**） | 68.0 / 76.5 / **86.6 / 86.5**    | 47.90%   |
| 官方矢量（换稿后）     | 46.0 / 53.1 / **66.5 / 67.0**    | 37.46%   |
| 本次（ρ=2.8 膨胀）     | 68.0 / 77.7 / **86.6 / 86.5**    | 47.77%   |

⚠️ **墨水占比只当旁证**：描摹稿的过填/糊边会把"线宽"和"填缝"搅进同一个数（本项目两者恰好都指向 ρ≈2.8~2.85，但不能指望每次都一致）。

**做法**：给上色的 path 加**同色渐变描边**，等价于对墨迹做半径 ρ = `stroke-width`/2 的 Minkowski 膨胀，用 `stroke-linejoin="round"` 让凸角按规范倒圆（logo 辫子的尖端随之自然变圆）：

```xml
<path fill="url(#gradient_0)" stroke="url(#gradient_0)" stroke-width="5.6" stroke-linejoin="round" d="…" />
```

- **比手工 offset 干净得多**：Clipper 之类做偏移得先把曲线展平成折线（弧变成几百段小线段，§5.15 好不容易拿到的"真圆弧"当场丢掉）；描边把这件事交给渲染器，`d` 一个字节都不用改，文件只涨 76 B（2099→2175）。
- **膨胀量怎么定**：扫 ρ（内容单位），每档按上面的口径量线宽 + 与旧版比 IoU/色差，四项对齐即为答案（本项目 ρ=2.8 ⇒ `stroke-width="5.6"`）。
- **重算最外层 `transform`（本次唯一踩的坑）**：膨胀是**四边各外扩 ρ**，必须按**膨胀后的盒子** `(bx−ρ, by−ρ, bw+2ρ, bh+2ρ)` 套 §1.1 两式：
  `s = 1024 / max(bw+2ρ, bh+2ρ)`；`tx = (1024 − (bw+2ρ)·s)/2 − (bx−ρ)·s`；`ty = (1024 − (bh+2ρ)·s)/2 − (by−ρ)·s`。
  展开后 `tx = (1024 − bw·s)/2 − ρ·s + ρ·s` —— 最长边是**高度**时后半两项正好抵消，只剩 `tx = (1024 − bw·s)/2`；`ty = ρ·s`。
  ⚠️ 我第一次写成 `(1024 − bw·s)/2 + ρ·s`，整图右移 10.8px（IoU 0.98→0.85、平均色差 1.4→17），还据此"量"出一个假的 ρ=2.2 最优解。**别凭公式记忆：写盘后先量可见盒左右余量是否相等。**
- **Flutter 兼容已核（本机 pub cache）**：`vector_graphics_compiler` `lib/src/svg/parser.dart` L1480–1485 把 `stroke="url(#…)"` 记成 `shaderId`（L2192 / L2281 用 `getGradient()` 解析 ⇒ **渐变描边是支持的**）；`stroke-linejoin` 支持 miter/bevel/round（L1199）。`OpenAI.svg` 是全仓库**唯一**用 `stroke` 的文件（其余 36 个仍全是纯 `fill`）。
- **验收（写盘后实测）**：线宽四项回到目标值；与旧版 IoU > 0.98、并集平均色差 < 2/255；可见盒最长边 = 1024 且左右余量相等；`transform` 计数 1、无 `style`/`filter`/`mask`、`url(#…)` 全部可解析。

### 5.17 形状缩放白名单：「方形图案」图标缩 10% / 5%（2026-09-28 定稿，规则见 §1.1）

**规则**：只有**用户明确点名**的「方形图案」图标才做等比例缩小（`k = 0.90`），其余一律保持「最长边铺满 1024」。

### 5.18 「近方形内容」要四边紧贴画布：只能横向补足（以 `OpenAI.svg` 为例）

**问题**：官方 OpenAI 矢量的内容盒是 **256.03 × 259.53（宽/高 = 0.9865）** —— 字形天生比宽高 1.35%。按 §1.1 等比归一（最长边 = 1024、另一方向居中留白）后必然**左右各留 6.75px**，而上/下顶满。实测改前可见盒 = **1010.50 × 1024**（左 6.75 / 右 6.75，相等），用户判定为"左右两边没有紧贴画布边缘"。

**为什么不能靠等比缩放或旋转解决**

- 等比放大到宽度铺满 1024 需要 +1.336%，高度就变成 1038.6 → 上/下各被 viewBox 裁掉 6.85px，而 OpenAI 辫子尖端的真实圆角半径只有 ~2.9px（§5.15），会被切出**明显平头**；
- 旋转不行：6 重对称图形转 60° 与原图重合（没变化）、转 30° 变成另一种朝向（logo 会"歪"）；小角度旋转则直接违反品牌标准朝向。

**做法**：横向单独补足 —— 最外层 `transform` 用**非等比两参数**形式（§1.1 的**唯一例外**）：

```xml
<g transform="translate(11.0206 10.8145) scale(3.9139042 3.8623049)">   <!-- sx/sy = 1.013360 -->
```

- 做法本身仍是「按实测可见盒解映射」：`sx = 1024 / 内容盒宽`、`sy = 1024 / 内容盒高`、`tx = -sx·Cx0`、`ty = -sy·Cy0`；`d` 与 `stroke` 一字未动。
- **代价**：横向比纵向多 **1.336%**（1024px 下 13.7px；32px 显示尺寸下约 0.4px，肉眼不可辨）。这是"四边紧贴"与"绝不形变"之间唯一的取舍 —— 下次遇到同类需求**先量化长宽比、再让用户定**。
- **验收**：4096 渲染实测可见盒 **1024.000 × 1024.000，四边余量全 0**；`transform` 计数仍 1、无 `<style>/<filter>/<mask>/xlink:`、`url(#gradient_0)` 可解析、CRLF 行尾与 15 行版式不变。
- **Flutter 兼容已核**：`vector_graphics_compiler`（本机 pub cache）`lib/src/svg/parsers.dart` L114–120 `_parseSvgScale` 明确支持 1~2 个参数（`params.length < 2 ? x : params[1]`）✓。
- ⚠️ **别顺手"修回"等比**：§1.1「非 1:1 图标不要拉伸铺满」对**其余 36 个图标**仍然生效，本条是用户明确要求的特例。
